Sentinel: Devin as a required gate on every PR

A normal contributor opens a PR. Sentinel attaches Devin as a required reviewer that fixes docs, runs a control-mapped compliance scan, remediates security findings behind a human-approved PR, and blocks merge until the gate is green — with an audit trail.

The loop, end to end

Six steps from “PR opened” to “merge unblocked”

The orchestrator does zero engineering — it routes events and drives the gate. Devin does all the work, in its own container. A human approves the one thing that touches security.

1
GitHub

A PR is opened

GitHub fires pull_request.opened through a tunnel to the orchestrator. It first guards against itself — any sentinel/* branch or Devin-authored PR is skipped, so the loop can’t recurse.

2
Orchestrator

Set the gate, dispatch Devin

The orchestrator sets the required check to pending and starts a Devin session, handing it the playbook as its job description.

gate →devin/compliance = pending · “Sentinel reviewing”
3
Devin

Fix the docs — on the branch, no gate

Devin clones the diff, checks docs against it, rewrites drift, and commits straight to the feature branch. Docs are low-risk, so they need no human approval.

commit →docs: sync documentation for PR #3
4
Devin

Scan, then remediate behind a proxy PR

Devin runs the 8-scanner suite, maps every finding to an 800-53 control, fixes what’s fixable, and opens a separate proxy PR with those changes — files tickets and appends POA&M rows along the way.

proxy →PR #4 · sentinel/compliance-3 (Dockerfile hardening, license headers)
5
Human

A human approves the security fix

The proxy PR is the one place a person is in the loop — federal change-control. Merge it and the fix lands on the branch; the gate reflects your decision.

gate →devin/compliance = pending · “awaiting proxy PR #4 approval”
6
Orchestrator

Gate flips — merge unblocked

The poller sees the proxy merged, re-pins the check to the PR’s live head, and turns it green. Because devin/compliance is a required check, the PR couldn’t have merged until this moment.

gate →devin/compliance = success · “remediations merged (proxy PR #4)”
The part that looks confusing

Two different Devins are commenting on your PR

You saw a “Devin Review” comment and asked why its findings weren’t auto-fixed. That’s because it isn’t Sentinel — it’s Devin’s built-in reviewer, which only advises. Here’s the difference on PR #3.

Devin’s native reviewer

“Devin Review found 5 potential issues”

app.devin.ai/review · a formal PR review, posted automatically on every PR
Advisory only — nothing is auto-fixed
  • Built-in Devin feature, independent of our integration
  • Leaves code-quality comments, like a human reviewer would
  • Acts on nothing — no commits, no PRs
Sentinel (our flow)

“Sentinel compliance review — PR #3”

an issue comment from playbook.py · docs fixed here, 6 findings remediated in a proxy PR
Actually remediates
  • Docs drift committed to the branch
  • demo.Dockerfile hardened (+28 / −6)
  • Apache license headers added to normalize.py (+194 / −52)
  • Delivered as proxy PR #4 — merged after your approval
The mental model

What gets fixed, what gets flagged

Sentinel routes each finding by risk. That routing is the whole design — not everything should be auto-applied, and not everything needs a human.

Finding typeWhat Sentinel doesHuman?
Docs driftCM-2 · CM-3 · SA-5 Rewritten and committed to the feature branch directly Auto-applied
Fixable security / hardeningRA-5 · CM-6 · IA-5 · SA-11 Fixed in a separate proxy PR you review and merge Approval gate
Findings needing judgmentSA-11 · SR-3 Filed as a ticket + a POA&M row mapped to its control Tracked, you decide
Code-quality notesDevin native review Left as advisory comments — Sentinel doesn’t touch them Advisory
Your question: why not just use Devin’s dashboard?

Two dashboards, two jobs

They don’t compete. Devin’s dashboard is the best view of one session’s inner work — so Sentinel links out to it rather than rebuilding it. Sentinel’s dashboard is the thing Devin’s can’t be: the fleet-and-compliance posture a VP or ISSO signs off on.

Use Devin’s for

One session, up close

  • The live plan and terminal
  • Files Devin touched, step by step
  • Steering a single run
Sentinel owns

The fleet & the audit

  • Every PR’s gate state at a glance
  • Findings rolled up by 800-53 control
  • POA&M / SSP burn-down + MTTR
  • The ticket board and event trail

The division of labor: Sentinel is the compliance cockpit and deep-links into Devin for any single-session drill-down. We don’t reproduce Devin’s session view — we surface the one thing it was never meant to show: whether the whole program is in control.

The architectural decisions

Six calls that make it a control, not a script

01

Devin is the primitive

The orchestrator writes zero code. It dispatches a session and observes — every fix, PR, and comment is Devin's. Swap the playbook, not the plumbing, to retarget it.

02

The gate is a real GitHub check

Sentinel sets a devin/compliance commit status; branch protection makes it required, so a PR genuinely cannot merge until Sentinel is green.

03

Risk-routed autonomy

Docs auto-commit (low-risk); security fixes go to a human-approved proxy PR; judgment calls become tickets + POA&M. Not everything should be auto-applied.

04

Two loops, one poller

Issue-remediation (issue → PR that Closes #N) and PR-review (gate + proxy PR) are distinct triggers that share one tracking loop and one state store.

05

Built to survive a real repo

Idempotent status writes, live-head re-pin after a squash-merge, proxy-PR detection by branch, blocked-as-ready, and a self-recursion guard — the failure modes a live PR actually hits.

06

One container, reproducible

FastAPI serves the API and the dashboard; SQLite for state; a background async poll loop; a single Docker image with pinned deps. docker compose up is the whole stack.

Python 3.12 · FastAPI + Uvicorn · httpx · SQLite · Docker (single pinned image) · Devin API · GitHub REST · cloudflared for webhook delivery
